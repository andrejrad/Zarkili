2. **NEW-DEBT-U closed (blocking fix):** Migrated `updateEmail` → `verifyBeforeUpdateEmail` in `auth/repository.ts`. Firebase email enumeration protection was rejecting `updateEmail` with `auth/operation-not-allowed`. New flow sends a verification link; auth email is unchanged until the user clicks the link.
3. **`toUserFacingAuthError` bug fixed:** The helper was stripping `.code` from the wrapped error, making upstream callers unable to distinguish Firebase error codes. Fixed with typed cast (no `any`, no lint regression).

### Decisions Made
1. Decision: Use `verifyBeforeUpdateEmail` instead of `updateEmail`.
   - Why: Firebase email enumeration protection (enabled on `zarkili-dev-a1b1c`) blocks `updateEmail` → `auth/operation-not-allowed`. `verifyBeforeUpdateEmail` is the correct migration path per Firebase docs.
   - Impact: Email address in Firestore profile is NOT updated immediately; it refreshes on next sign-in after the user confirms the link. Success message updated to explain this.

2. Decision: Remove Firestore profile write from `updateEmailAddress`.
   - Why: Writing the new email to Firestore before the user confirms the link would create a stale/incorrect profile. The correct pattern is: send verification link → user clicks → Firebase updates auth email → next `getCurrentSession` call reads fresh email from `auth.currentUser`.
   - Impact: `mockSetDoc` is now asserted `not.toHaveBeenCalled()` in the test.

3. Decision: Relax `updateProfile` validation — only `firstName` required (lastName optional).
   - Why: Single display name field in the UI; user may have a single-word name. Splitting on whitespace: first token = firstName, rest = lastName.
   - Impact: `lastName` validation removed from `submitAccountProfile`; error message changed to "Display name is required."
